# REQ-003: Configurable Workflow MVP

## ID и цель

**ID:** REQ-003  
**Статус:** draft  
**Версия Product OS:** 0.4.0 — draft  
**Цель:** превратить [Configurable Workflow Foundation](../01-foundation/configurable-workflow-foundation) в конкретное MVP-требование для запроса на расчёт и перевозки.

REQ-003 не заменяет принятые бизнес-решения. Он уточняет минимальный проверяемый объём реализации D-065…D-074 для MVP.

## Область MVP

Workflow подключается только к:

- запросу на расчёт;
- перевозке.

Рейс, финансы, договоры, заявки к договору и другие процессы могут оставаться описанными в Product OS, но не входят в обязательный объём REQ-003.

## Минимальная модель

Минимальная модель не привязана к конкретной SQL-базе, ORM или названиям таблиц. Реализация должна поддерживать следующие понятия:

| Понятие | Назначение |
|---|---|
| Workflow template | Шаблон процесса для типа объекта: request или shipment |
| Workflow version | Неизменяемая версия шаблона, используемая новыми объектами |
| Workflow stage | Этап с внутренним названием, клиентским названием, порядком, видимостью и правами |
| Workflow transition | Разрешённый переход между этапами с правилами роли и обязательного комментария |
| Workflow instance | Экземпляр workflow, привязанный к конкретному запросу или перевозке |
| Workflow history | История переходов с автором, датой, предыдущим и новым этапом, комментарием |

## Request workflow v1

Запрос на расчёт создаётся на Request workflow v1.

| Код | Внутренний этап | Клиентская видимость |
|---|---|---|
| `new` | Новый | Да |
| `manager_review` | Проверка менеджером | Да |
| `data_required` | Требуются данные | Да |
| `sent_to_logistician` | Передан логисту | Да |
| `rate_search` | Поиск ставки | Да |
| `rate_received` | Ставка получена | Да |
| `recalculation` | Перерасчёт | Да |
| `offer_to_client` | Предложение клиенту | Да |
| `approved` | Согласовано | Да |
| `closed` | Закрыто | Да |

## Дополнительные состояния

Для Request workflow v1 и Shipment workflow v1 должны быть доступны дополнительные состояния:

- Проблема;
- Приостановлено;
- Отменено.

Переход в дополнительное состояние требует комментарий. Клиент получает только разрешённое клиентское название и не получает внутреннюю причину, если она не опубликована менеджером.

## Правила

1. Объект сохраняет версию workflow, с которой был создан.
2. Изменение активной версии не меняет старые объекты.
3. Пользователь видит только допустимые переходы своей роли.
4. Каждый переход записывается в историю.
5. Обязательный комментарий проверяется до перехода.
6. Клиент не получает internal name, internal comment и скрытые этапы.
7. Клиенту возвращается только разрешённое клиентское название.
8. После обновления страницы текущий этап сохраняется.

## Что должно появиться в интерфейсе

- текущий этап в карточке запроса;
- допустимые действия менеджера;
- допустимые действия логиста;
- текущий этап в карточке перевозки;
- история переходов;
- безопасный клиентский статус;
- read-only список шаблонов в кабинете администратора.

## Не входит в MVP

- drag-and-drop конструктор;
- создание шаблонов через UI;
- динамический form builder;
- автоматические эскалации;
- массовая миграция старых объектов;
- отдельные процессы для каждого вида транспорта.

## Критерии приёмки

### AC-001 — Request workflow v1

Новый запрос на расчёт создаётся с workflow instance на активной версии Request workflow v1 и начальным этапом `Новый`.

### AC-002 — Shipment workflow v1

Новая перевозка создаётся с workflow instance на активной версии Shipment workflow v1 и начальным этапом `Подготовка`.

### AC-003 — Запрещённый переход

Если переход не описан в active workflow version объекта, приложение отклоняет переход и не меняет текущий этап.

### AC-004 — Ролевое ограничение

Пользователь не может выполнить переход, который не разрешён его роли. В интерфейсе такой переход не показывается, а API также отклоняет попытку.

### AC-005 — История переходов

Каждый успешный переход сохраняет запись в workflow history: объект, версия, предыдущий этап, новый этап, автор, роль, дата и комментарий при наличии.

### AC-006 — Сохранение после reload

После обновления страницы карточка запроса или перевозки показывает тот же текущий этап, который был сохранён последним успешным переходом.

### AC-007 — Клиентский API

Клиентский API не возвращает internal name, internal comment, скрытые этапы, staff-only поля и внутреннюю историю.

### AC-008 — Версионирование

Если активируется новая версия workflow, уже созданный запрос или перевозка остаётся на версии, с которой объект был создан.

### AC-009 — Обязательный комментарий

Если transition требует обязательный комментарий, переход без комментария отклоняется до изменения этапа.

### AC-010 — Регрессия основных сценариев

Существующие основные сценарии приложения не ломаются: создание запроса, передача логисту, добавление ставки, формирование клиентской цены, создание перевозки и клиентский просмотр статуса продолжают работать на workflow v1.
