# Контракты страниц Foundation Gate

## Статус и назначение

**Статус:** ready for implementation в пределах [Foundation Gate](../07-mvp/foundation-gate).<br>
**Назначение:** дать интегратору минимально однозначный контракт обязательных экранов без полного редизайна и без выдумывания открытых бизнес-правил.

Логический ID страницы не предписывает конкретный Next.js route. Интегратор выбирает path-based или стабильный hash-контракт по REQ-005, документирует его и доказывает direct open, Reload, Back и Forward.

## Общий контракт каждого экрана

Каждый экран ниже обязан иметь:

1. серверную проверку session, membership, tenant/workspace, роли и object scope;
2. стабильную ссылку на раздел или объект;
3. только разрешённые поля в server payload;
4. состояния `loading`, `empty`, `error`, `forbidden` и `not found` без утечки существования чужого объекта;
5. защиту повторной отправки для мутаций;
6. audit критических действий;
7. рабочий layout на 360, 375 и 390 px без page-level horizontal overflow.

Роли Gate: `client`, `manager`, `logistician`, `tenant admin`. Platform admin, moderator и финальная organization-admin модель не входят в Gate.

## Auth и tenant scope

### AU-001 — Вход

- Доступ: неавторизованный пользователь.
- Действия: вход, восстановление, переход к разрешённой регистрации.
- После входа: только безопасный return target внутри доступного scope.
- Ошибки: неверные данные, заблокированный аккаунт, сетевой сбой, истёкшая сессия.
- Запрет: ответ не раскрывает, существует ли введённый email.
- Приёмка: `/app` без сессии закрыт; logout инвалидирует доступ; вход проверен каждым Gate-account.

### AU-003 — Подтверждение и восстановление

- Verification и recovery имеют разные состояния и контексты.
- Успех показывается только после действительного обмена code и ожидаемого auth/session результата.
- Пустой, ошибочный, неверный и истёкший callback показывают ошибку, не `verified=1`.
- Recovery form недоступна без действительного recovery context.
- Повторная отправка и техническая ошибка не раскрывают секреты.

### ORG-002 — Участники, роли и приглашения

- Gate-доступ: tenant admin текущего workspace.
- Данные: WorkspaceMembership, статус, Gate-роли, client-company scope и назначения.
- Действия: создать/пригласить тестовое membership по реализованному механизму, изменить Gate-роль, приостановить доступ.
- Каждое изменение роли или membership аудируется.
- Запреты: нельзя управлять другим workspace, выдавать platform admin/moderator или обходить tenant scope.
- Self-service onboarding не требуется: тестовые tenants разрешено provision вручную и документированно.

## Клиент

### CL-001 — Главная клиента

- Scope: только client company пользователя внутри текущего workspace.
- Данные: свой менеджер, свои запросы, доступные Shipment, необходимые действия и опубликованные tracking-события.
- Счётчики открывают реальные списки с тем же фильтром.
- Запрещены staff KPI, задачи сотрудников, управление ролями, себестоимость, маржа, перевозчик и водитель.

### CL-002 — Новый запрос

- Поля формы: весь перечень REQ-001/D-025; наличие поля не делает его автоматически обязательным.
- Для отправки в `manager_review`: доступная client company и контакт из авторизованного scope, откуда, куда, груз, вес и объём. Остальная обязательность по виду перевозки остаётся TBD.
- Действия: сохранить draft с tenant/client scope, отправить валидный draft в `manager_review`.
- В маршруте, компании, контактах и телефоне нет предзаполненных demo-значений или жёсткого города. Реальные company/contact могут безопасно подставляться из авторизованного scope.
- Ошибка шага не стирает введённые данные; повторная отправка идемпотентна.
- Создаётся QuoteRequest только для доступной client company текущего пользователя.

### CL-003 — Мои запросы

- Список и фильтры только своих QuoteRequest.
- Показываются client labels, а не internal stage codes.
- Карточка открывается по стабильной ссылке.
- Запросы другой client company или tenant отсутствуют в payload.

### CL-004 — Карточка перевозки

- Данные: маршрут, груз, актуальная плановая дата, безопасный статус, Trips, опубликованный tracking, клиентские документы и менеджер.
- Запрещены RateQuote, себестоимость, маржа, перевозчик, водитель и staff comments.
- Reload открывает тот же Shipment; чужой object ID обрабатывается по non-disclosure contract.

### CL-005 — Список рейсов

- Только Trips доступного Shipment: порядок, маршрут, безопасный статус и опубликованные события.
- Driver/carrier fields отсутствуют в client payload.
- Ссылка Trip стабильна либо вложенное состояние полностью восстанавливается из URL.

### CL-006 — Документы

- Document имеет tenant scope, object link, версию и client visibility.
- Клиент видит/скачивает только опубликованные ему документы.
- Upload доступен только для разрешённых типов и объектов.
- Staff-only document нельзя скачать по прямому ID; замена сохраняет версию и audit.

## Менеджер

### MG-001 — Главная менеджера

- Scope: назначенные или явно разрешённые клиенты и объекты текущего tenant.
- Реальные очереди: manager review, без ставки, предложение без ответа, Shipment без обновления.
- Счётчики совпадают со списками при одинаковом scope; иной фильтр явно подписан.
- Каждая карточка открывает реальный объект.

### MG-002 — Карточка клиента

- Данные: client company, контакты, пользователи, основной менеджер, запросы, предложения, договорные основания, Shipment, документы и история.
- В Gate менеджер видит только назначенного клиента либо явно разрешённый scope.
- MG-007 передача клиента относится к Post-Gate; изменение manager ID не может быть обходом.

### MG-003 — Карточка запроса

- Данные: QuoteRequest, логист, RateQuote versions, выбранная ставка, итоговая цена/маржа, CommercialOffer versions и history.
- Кнопки строго соответствуют разрешённым transitions REQ-003.
- Произвольная установка stage запрещена.
- Действия другого tenant или неразрешённого manager отклоняются сервером.

### MG-004 — Коммерческое предложение

- Данные: выбранный RateQuote, итоговая цена, услуги, client terms и версия.
- Действия: сохранить/создать версию, отправить, ответить новой версией после уточнения.
- Low-margin threshold не утверждён: интегратор не придумывает число и не включает автоматический trigger без решения.
- Client payload не содержит себестоимость, подрядчика или маржу.

### MG-005 — Карточка перевозки

- Shipment ссылается на QuoteRequest, offer version и договорное основание.
- Данные: внутренний stage, ответственный логист, Trips, документы, tracking drafts и audit.
- Менеджер меняет плановую дату только с причиной и сохранением старого значения.
- Внутренний переход Shipment и публикация клиенту являются разными действиями.

### MG-006 — Публикация события

- Очередь внутренних tracking events, ожидающих клиентской публикации.
- Действия: подготовить client text, опубликовать, исправить новой версией, вернуть на уточнение.
- Internal comment, перевозчик, водитель и закрытые контакты не копируются.
- История публикаций не удаляется.

### MG-008 — Минимальный договорный gate

Полный договорный модуль не требуется. Gate хранит:

- тип основания: годовой/рамочный договор и заявка к договору;
- номер или внутреннюю ссылку;
- дату подписания;
- подписанный документ либо подтверждённую ссылку;
- автора и время фиксации.

Без валидного основания UI скрывает/блокирует создание Shipment, а сервер отклоняет прямой запрос. Для Gate факт фиксирует manager; постоянный actor остаётся TBD.

## Логист

### LG-001 — Очередь расчётов

- Только назначенные логисту запросы текущего tenant.
- Данные: приоритет, возраст, полнота, ожидаемая дата ставки при использовании H-003.
- Действия: принять в работу, вернуть на уточнение, открыть расчёт.
- Итоговая клиентская цена и маржа не возвращаются логисту в Gate.

### LG-002 — Проверка запроса и расчёт

- Проверка полноты по D-042.
- Возврат в `data_required` требует перечень недостающих данных.
- Каждый RateQuote отдельный и содержит D-056 плюс маршрут, транспорт, валюту и источник/партнёра.
- Создание RateQuote не меняет stage: логист добавляет минимум два варианта в `rate_search`, затем отдельным действием переводит запрос в `rate_received`.
- Перерасчёт не включается до решения actor; существующая ставка не перезаписывается.
- Логист не устанавливает CommercialOffer или client price.

### LG-003 — Минимальное согласование с партнёром

- Данные относятся только к выбранному RateQuote: партнёр, условия перевозки/оплаты, документ/ссылка, дата и автор.
- Порядок exim.kz: сначала клиентское договорное основание, затем партнёрское — D-047.
- Не смешивается с Exchange response или договором платформы.
- В Gate это может быть секция QuoteRequest/Shipment; отдельный route не обязателен, если состояние восстанавливается по object URL.

### LG-004 — Исполнение перевозки

- Только назначенные Shipment текущего tenant.
- Данные: внутренний lifecycle exim.kz, Trips, carrier/driver, проблемы и tracking.
- Назначенный логист создаёт Trip в `preparation` идемпотентно. Обязательные поля: parent Shipment, sequence, откуда, куда, transport mode и назначенный логист; Trip получает отдельный стабильный ID.
- Переход `preparation → transport_assigned` требует внутренний partner/carrier и mode-specific transport reference; для road acceptance fixture — машину и водителя. Далее Gate разрешает только `transport_assigned → loading → in_transit` по матрице REQ-003.
- Переходы ограничены матрицей REQ-003.
- Логист создаёт внутренние события и не публикует их клиенту напрямую.
- `problem`, `paused`, `cancelled` как stages отключены до определения полномочий; проблему можно записать отдельным audit/event по D-049.

### LG-005 — Документы от завода

- Поля: тип, объект, версия, автор, дата и client visibility.
- По умолчанию документ внутренний.
- Клиентская публикация — отдельное разрешённое действие.
- Прямой object ID не обходит tenant/client visibility.

## Tenant admin

### AD-001 — Read-only workflow

- Список активных WorkflowTemplateVersion для QuoteRequest, Shipment и минимального Trip.
- Показывает stages, transitions, Gate-role permissions и client labels.
- В Gate нет create/edit/activate/delete controls.
- Tenant admin A не читает приватный template B.
- Полный editor относится к Post-Gate и OQ-030/OQ-044.

### AD-002 — Пользователи и роли tenant

- Только WorkspaceMembership текущего tenant.
- Gate-роли: client, manager, logistician, tenant admin.
- Назначение client company и рабочих объектов.
- Изменение роли аудируется.
- Нельзя выдать platform admin/moderator или изменить другой tenant.

### AD-003 — Tenant audit

- Фильтры: объект, пользователь, действие, дата.
- События: membership/role changes, workflow transitions, цены, tracking publication и tenant-admin actions.
- Обычные роли не меняют audit records.
- Tenant admin видит только свой tenant; клиент не получает tenant audit.
