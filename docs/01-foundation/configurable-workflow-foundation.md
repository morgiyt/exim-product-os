# Configurable Workflow Foundation

## ID и цель

**ID:** FOUNDATION-004
**Цель:** заложить гибкую систему Private OS, в которой этапы заявок, перевозок, рейсов, договоров и финансов не зашиты в код, а настраиваются для tenant через workflow-шаблоны без переделки всей платформы.

Workflow Foundation относится к приватному операционному контуру. Он не определяет lifecycle Exchange и не делает биржевые объекты публичными автоматически.

## Принцип

```text
Фиксированные сущности (данные)
        ↕
Workflow-шаблон (процесс)
        ↕
Экземпляр процесса на объекте
        ↕
История этапов и изменений
```

Сущности хранят бизнес-данные конкретного tenant. Шаблоны определяют допустимые этапы, переходы, права и клиентскую видимость. Права workflow применяются только после проверки membership и entitlement на уровне платформы.

## Фиксированные сущности (D-065)

Не меняются при изменении процесса:

| Сущность | Назначение |
|---|---|
| Клиент | Пользователь клиентской компании |
| Компания | Клиентская или партнёрская организация |
| Лид | Первичный интерес |
| Запрос на расчёт | Потребность клиента на расчёт |
| Ставка | Вариант цены от логиста / партнёра |
| Коммерческое предложение | Итоговое предложение клиенту |
| Договор | Годовой или рамочный договор |
| Заявка к договору | Документ на конкретную перевозку |
| Перевозка | Исполняемый заказ |
| Рейс | Отдельное отправление |
| Документ | Файл с правилами видимости |
| Задача | Поручение с дедлайном |
| Платёж | Счёт и оплата |
| Событие | Внутреннее или клиентское обновление |

Этапы этих объектов **не являются** частью кода приложения.

## Workflow-шаблон (D-066)

Шаблон принадлежит tenant или является разрешённым системным шаблоном платформы и привязан к типу объекта: запрос, перевозка, рейс, договор, заявка, платёж и др. Правила наследования системных и tenant-шаблонов остаются OQ-044.

Каждый шаблон содержит:

- список этапов;
- допустимые переходы;
- права ролей;
- клиентские настройки;
- настраиваемые поля;
- правила уведомлений и эскалаций.

## Этап шаблона (D-067)

| Поле | Обязательность | Описание |
|---|---|---|
| Внутреннее название | Да | Для сотрудников tenant; `exim.kz` — первая конфигурация |
| Название для клиента | При видимости | Публикуемая формулировка |
| Порядок | Да | Сортировка в UI |
| Цвет | Да | Визуальный маркер |
| Ответственные роли | Да | Кто ведёт этап |
| Видимость клиенту | Да | Показывать / скрыть |
| Обязательные поля | По настройке | Custom fields |
| Обязательный комментарий | По настройке | При переходе |
| Обязательный файл | По настройке | При переходе |
| Допустимые следующие этапы | Да | Граф переходов |
| Уведомления | По настройке | Кому и когда |
| Ожидаемый срок | Нет | SLA этапа, необязательно |

## Версии шаблонов (D-068)

```text
WorkflowTemplate v1 (активна для новых)
WorkflowTemplate v2 (новая версия)
        ↓
Старые перевозки → остаются на v1
Новые перевозки → используют v2
История этапов → не ломается
```

Правила:

- объект при создании получает актуальную версию шаблона;
- существующий объект не мигрирует автоматически;
- история этапов хранит ссылку на версию и код этапа;
- изменение шаблона не переписывает прошлые записи.

## Аудит изменений (D-069)

Любое изменение процесса, этапа, поля или перехода хранит:

- старое значение;
- новое значение;
- автора;
- дату;
- причину.

## Настраиваемые поля (D-070)

Типы без переписывания интерфейса:

| Тип | Пример |
|---|---|
| Текст | Номер машины |
| Число | Вес |
| Дата | Дата готовности |
| Список | Тип перевозки |
| Файл | Фото груза |
| Чекбокс | Штабелирование |
| Пользователь | Ответственный |
| Компания | Перевозчик |

Поля привязываются к типу объекта и/или к конкретному этапу.

## Права на этап (D-071)

Для каждого этапа задаются права одной или нескольких ролей Private OS внутри tenant:

- менеджер;
- логист;
- бухгалтер;
- юрист;
- руководитель;
- администратор.

Типичные права: просмотр, редактирование, переход, публикация клиенту, отмена.

## Клиентский слой этапа (D-072)

Отдельно от внутренних настроек:

| Настройка | Описание |
|---|---|
| Показывать этап | Да / нет |
| Клиентское название | Формулировка для ЛК |
| Клиентское описание | Пояснение статуса |
| Комментарий менеджера | Обязателен ли перед публикацией |

Клиент не видит внутренние названия, цвета для staff-only этапов и служебные поля.

## Универсальные механизмы (D-073)

Единые для всех workflow:

- **задачи** — поручения с исполнителем;
- **дедлайны** — ожидаемый срок этапа;
- **уведомления** — in-app и позже внешние;
- **напоминания** — до и после дедлайна;
- **эскалации** — при просрочке или блокере.

## Базовый финансовый workflow (D-074)

Стартовый шаблон, **не окончательный процесс**:

```text
Счёт не выставлен
→ Счёт выставлен
→ Ожидается оплата
→ Частично оплачено
→ Оплачено
→ АВР отправлен
→ АВР подписан
→ Документы возвращены
→ Закрыто
```

Дополнительные состояния:

- Просрочено;
- Возврат;
- Спор;
- Отменено.

Будущая роль, утверждённая после OQ-030/OQ-044, сможет версионировать шаблон без изменения кода. В Foundation Gate editor отсутствует.

## Связь с текущими этапами логистики

Операционная часть D-058 после договорного gate (подготовка, погрузка, путь/граница, доставка и закрывающие документы) — **референсный Shipment template v1 для `exim.kz`**, а не универсальная жёсткая реализация. Расчёт и предложение относятся к QuoteRequest. Будущие изменения выполняются новой версией по правилам OQ-030/OQ-044.

## Роли с доступом

| Роль | Доступ |
|---|---|
| Tenant-администратор | В Gate — read-only просмотр. Возможность создавать и редактировать tenant-шаблоны после появления редактора — предлагаемая модель, OQ-030/OQ-044 |
| Platform-администратор | Возможное управление системными шаблонами по отдельным правам; точный scope — OQ-034/OQ-044 |
| Руководитель | Возможные просмотр/предложения изменений — draft до OQ-030 |
| Менеджер / логист / бухгалтер / юрист | Работа по этапам по правам |
| Клиент | Только клиентский слой этапов |

## Критерии приёмки

- этапы не зашиты в код приложения;
- шаблон, версия, экземпляр и аудит имеют tenant-владельца или явную системную область;
- пользователь tenant A не может читать или менять workflow tenant B;
- отсутствие entitlement модуля блокирует действие даже при наличии роли;
- новая версия шаблона не ломает историю старых объектов;
- клиентский API не возвращает staff-only этапы и поля;
- переход без обязательных полей / комментария / файла блокируется;
- каждое изменение шаблона попадает в аудит;
- если финансовый workflow входит в выбранный релиз, он работает как версионируемый шаблон; в Gate он не требуется.

## Ограничения

- Foundation Gate — предустановленные версии и read-only просмотр шаблонов;
- минимальный редактор шаблонов, не полный BPMN, относится к последующему этапу после OQ-029/OQ-030;
- внешние каналы уведомлений — позже (D-017);
- миграция объектов между версиями шаблона — открытый вопрос OQ-031;
- наследование системных и tenant-шаблонов — открытый вопрос OQ-044.
